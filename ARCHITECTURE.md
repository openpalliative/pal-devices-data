# pal-devices-data: архитектура

Срез 11.10.2026. Инструмент «Кто выдаёт изделия», префикс `dv`, порт 8702, на Pages `/pal-devices-data/`. Документ стоит поверх `../PLATFORM.md` (техника) и `../UX_MAP.md` (адреса, тексты, переходы). Если здесь что-то с ними расходится, правы они, кроме решений, отмеченных ниже как «решение репо» с причиной

Идея проекта: бытовое название → вид НКМИ → код → кто выдаёт (медорганизация или Соцфонд) → основание дословно → срок. Плюс ветка «лечебное питание»

## 0. Ключевые решения

| # | Решение | Почему |
|---|---|---|
| A1 | Канон данных и пайплайн по варианту «от данных»: постраничная подпись скана, НКМИ через `meta.csv`, флаг `retired`, fail closed, две даты на сайте | честнее и не требует ручной работы каждую неделю |
| A2 | Поиск, нормализация, golden-карточки 303260/280360/113810, показ коллизий норм по варианту «от людей» | это то, ради чего семья открывает сайт |
| A3 | Адреса только из UX_MAP §2.4. Лист «что просить» живёт на `/list/` и печатается оттуда. Состояние листа нигде не хранится, предвыбор одного кода приходит фрагментом `#device=<код>` (ключ из белого списка UX_MAP §4.1) | query уходит в логи Pages, а набор кодов (трахеостома, ИВЛ) выдаёт диагноз, поэтому без `localStorage` и без `?c=` |
| A4 | Канал выдачи считается по двум полям: `fn2` (сноска 2 в перечне) и `tsr_2347r` (входит ли вид в федеральный перечень ТСР: `yes`, `no` только с цитатой, `by_fn2` по сноске 2, `unknown`). В MVP у всех позиций без сноски `tsr_2347r: unknown` | п. 26 положения о паллиативной помощи отправляет в Соцфонд всё из перечня ТСР, а не только позиции со сноской. Электроколяска 207920 без сноски, но похожа на ТСР. Своих выводов сверх цитат не делаем |
| A5 | Наблюдатель этого репо смотрит только НКМИ РЗН. Поиск новых редакций перечня изделий, перечня ТСР и перечня лечебного питания на pravo.gov.ru уходит в `pal-norms` (PLATFORM §6.3). `pipeline/fetch_pravo.py` здесь нужен только для разового скачивания и OCR известных eoNumber | один наблюдатель официальных публикаций на всю организацию |
| A6 | `verified` значит «строка сверена с изображением страницы скана и с НКМИ». Отдельное поле `legal_reviewed` в MVP везде `false`, поэтому плашка `draft(legal)` стоит на всех страницах | честно разделяем «сверено со сканом» и «проверено юристом» |
| A7 | Номера актов не пишем литералом ни в `content/`, ни в `templates/`, ни в текстовых полях данных. В текстах данных ссылка на норму пишется токеном `[[n:398n]]`, сайт подставляет ссылку через `norm()` или запасной заголовок из `data/sources.yaml` | content-lint и PLATFORM §2.2 |
| A8 | `stale_after_days: 90` для `data_date`. Автопроверка НКМИ показывается отдельной строкой со своей датой | стандарт 90, а еженедельная проверка - другой факт |
| A9 | `/nutrition/<id>/` = страница редакции перечня питания, `<id>` = eoNumber редакции. Позиции перечня (торговые названия) в MVP не публикуем | в перечне торговые наименования, решать мейнтейнеру (38-ФЗ). В UX_MAP поправить смысл `nut=` (строка в STATUS) |
| A10 | Ветку питания называем «Продукта нет в перечне», а не «диагноз вне перечня» | перечень перечисляет продукты, а не диагнозы, это видно по стр. 2 акта |
| A11 | `successor_code` (чем заменён старый вид) в MVP не ведём. Код, которого нет в новом перечне, показываем словами «Кода нет в новом перечне. Возможно, вид переименован, это проверяется» | эквивалентность видов - медицинское суждение |
| A12 | «Похожие изделия» не показываем. На карточке есть свёрнутый список «Другие позиции этой группы перечня» | иначе читается как подбор замены (ПП 1684) |
| A13 | PWA не включаем (`pwa: false`): на сайте нечего вводить и хранить, а перечень и статусы норм должны приходить свежими, без старой копии в кэше браузера | лист «что просить» печатается или сохраняется в PDF, этого хватает без service worker |

## 1. Что строим

### 1.1 MVP (этот прогон)

- `data/398n.csv`: 170 кодов, 29 со сноской 2, код 327610 на месте. Строка `verified:true` только после подписи страницы в `data/review/scan_pages.yaml`. Цель: подписаны все 14 страниц таблицы (стр. 3-16 скана)
- `data/348n.csv` по OCR 19 страниц скана плюс поправка 1195н. Что не подписано постранично, остаётся `verified:false` и не попадает в счётчики семьям
- дифф 348н → 398н считается в `export.py`
- `data/aliases.csv`: 30-50 бытовых названий без товарных знаков
- `channels.yaml`, `warnings.yaml`, `quotes.yaml`, `sources.yaml`
- `nutrition_3551r.csv`: три редакции (2023, 2024, 2025), сверены по первой странице
- снимок НКМИ `data/snapshots/nkmi.json` и `last_check.json`
- все страницы из раздела 2, 170 карточек, печать листа «что просить» A4
- workflows `pages.yml`, `checks.yml`, `watch.yml` (НКМИ), `sync-data.yml`, `release.yml`, шаблон issue «Предложить название»
- тесты и ворота раздела 7

### 1.2 Позже (не в этом прогоне)

| Что | Условие |
|---|---|
| Позиции перечня лечебного питания (наименование и форма дословно, `edition_added`, `edition_removed`) | решение мейнтейнера и юриста по торговым наименованиям |
| `tsr_2347r` по каждой позиции и `tsr_crosswalk.csv` с классификацией ТСР 86н | источник текста перечня ТСР в действующей редакции |
| `kits.yaml` (что входит в комплект к аппарату) | только с подписью медика |
| Реестр региональных актов о питании 18+ | в `pal-norms` или отдельным датасетом, после MVP |
| Ввод «отметьте позиции своей ИПРА» | после ревью юриста |
| Ветка «инвалидность есть, а в ИПРА позиции нет» с нормой | когда найдётся норма с цитатой. В MVP только строка `verified:false` и ссылка на сценарий `oral-refusal` |

### 1.3 Не делаем никогда

- бренды, модели, цены, продавцы, подбор аппарата и размеров, частоты замены
- учёт выдачи, склады, списки подопечных, мультиклиентский режим
- калькулятор номинала электронного сертификата и любые запросы к сайтам Соцфонда и ktsr: это сетевые проверки госсайтов РФ вне рамок
- медицинские пороги (например, «сколько часов без аппарата» из 505н п. 6) на карточках и листе

## 2. Страницы и маршруты

Базовый путь `/pal-devices-data/`. `site.nav` по UX_MAP §5.2: Поиск (`""`), Весь перечень (`list/`), Питание (`nutrition/`), Через кого получают (`channels/`). На всех страницах `draft(legal)`, `op-data-date` и в `head` дополнительно `<meta name="referrer" content="no-referrer">`, чтобы переходы на pravo.gov.ru не уносили адрес карточки

### 2.1 `/` Поиск

- H1 «Кто выдаёт изделия», фраза «Найдите аппарат или расходник по тому, как вы его называете. Покажем, кто его выдаёт и на каком основании»
- H2 «Как вы это называете?» как `label` поля. Подсказка «Например, откашливатель, кислород или подгузники». Форма отрисована с `hidden`, `dv-search` снимает атрибут. Запрос не пишется ни в адрес, ни в хранилище
- 6 быстрых кнопок: Откашливатель, Кислород, Трубка, Матрас, Подгузники, Коляска. Каждая - ссылка на якорь `#a-<alias_id>` в указателе ниже, поэтому без JS тоже работает. С JS кнопка подставляет слово в поле и показывает результаты
- результаты под полем в `aria-live="polite"`, до 12 штук:
  - карточка результата: вид по НКМИ, код, одна строка канала с иконкой и словом («Выдаёт медорганизация» или «Медорганизация или Соцфонд»), ссылка на карточку

  - если нашёлся код, которого нет в новом перечне (только сверенные строки 348н): «Этого кода нет в новом перечне» и ссылка на `/changes/#c-<код>`
  - пусто: статус UX_MAP §6 «Такого названия мы не нашли. Попробуйте другое слово или откройте весь перечень», ссылка на `/list/`, ссылка «Предложить название» на шаблон issue. Над ней строка «Не пишите в предложении имя, диагноз и регион»
- ниже: H2 «Названия по алфавиту»: бытовые названия группами по первой букве, у каждого ссылки на карточки (путь без JS)
- ниже: «Через кого получают изделия» одной строкой со ссылкой на `/channels/`, потом `op-data-date`

**Первый экран телефона 360×640:** шапка в две строки, `site.nav` строкой, H1 и фраза, поле поиска 48px с подписью, быстрые кнопки двумя строками. Плашка черновика на этой странице компактная (одна строка и ссылка «подробнее»), если платформа даст такой вариант, иначе обычная под быстрыми кнопками. Дата данных ниже сгиба

### 2.2 `/devices/<код>/` Карточка

Порядок блоков:

1. крошки «openpalliative › Кто выдаёт изделия › [название]»
2. H1 = основное бытовое название (`aliases.primary`), иначе имя вида НКМИ. Под ним строка «Вид по справочнику Росздравнадзора: [имя НКМИ] · код [код]» и «Как ещё называют: ...»
3. если строка не сверена или кода нет в последнем снимке НКМИ: `op-status unverified` с причиной
4. `draft(legal)`
5. H2 «Кто выдаёт», макрос `dv_channel(device)`:
   - без сноски 2: одно предложение крупно «Выдаёт медицинская организация, которая оказывает паллиативную помощь». Под ним `info`: «В перечне у этой позиции нет сноски о Соцфонде. Инвалидность и ИПРА перечень условием выдачи не называет». Ниже свёрнутый `<details>` «Если у человека есть инвалидность»: дословно п. 26 положения и строка `unverified` «Входит ли эта позиция в федеральный перечень реабилитационных средств, мы ещё не сверили»
   - со сноской 2: две ветки карточками рядом (на телефоне одна под другой): «Если инвалидности нет» → медорганизация; «Если у человека есть инвалидность» → Соцфонд по правилам обеспечения техническими средствами реабилитации. Про инвалидность сайт не спрашивает, показывает обе
   - если норма канала в снимке `pal-norms` имеет статус не `in_force`: вместо канала `op-status unverified` «Основание изменилось, проверяется» (fail closed)
6. H2 «Основание»: `op-quote` со строкой перечня (группа, подгруппа, вид, код, страница скана, ссылка на публикацию), п. 25 положения, при сноске 2 дословная сноска 2. У цитаты с `verified:false` статус «Не проверено»
7. H2 «Сколько ждать»: формулы из `pal-norms/deadline-rules` (правила `505n-vk`, `505n-transfer`), если правило есть, `verified:true` и норма `in_force`. Иначе `unverified` «Срок пока не сверен» и ссылка на «Нормы и сроки». Своих чисел в данных dv нет
8. H2 «Важно знать»: предупреждения из `warnings.yaml` статусом `info`, в том числе две коллизии: п. 25 положения ссылается на отменённый старый перечень, сноска 2 ссылается на п. 26 отменённого положения
9. строка «В старом перечне: было» / «новая позиция» / «не проверено»
10. H2 «Что дальше», кнопки:
    - «Не выдают? Попросить ответ на бумаге» → `xurl('obrashchenie-kit', 'case/', {new:1, s:'oral-refusal', device:код})`
    - «Добавить в лист „что просить“» → `list/#device=<код>`
    - «Что просить при выписке» → `xurl('home-care-kit', 'discharge/')`
    - «Основание» → `pn /acts/<norm_id>/`
11. `<details>` «Другие позиции этой группы перечня» ссылками
12. «Вернуться: ...» при `back=`, «Что ещё может пригодиться», `op-data-date` и строка автопроверки НКМИ

**Первый экран телефона:** крошки, H1 (до двух строк), строка НКМИ и кода, плашка черновика, заголовок «Кто выдаёт» и первое предложение канала

### 2.3 `/list/` Весь перечень и лист «что просить»

- H1 «Весь перечень», строка «[170] позиций в [7] группах. Сверено с официальной публикацией [дата]»
- фильтры (`dv-list`, без JS скрыты): поле «Найти в перечне», флажки «Только со сноской о Соцфонде», «Только новое по сравнению со старым перечнем»
- группы в `<details open>`: таблица «Вид по НКМИ (ссылка), Код, Кто выдаёт (иконка и слово), В старом перечне». На ширине до 720px строка таблицы становится блоком. С JS у каждой строки флажок «В лист»
- блок «Лист „что просить“»: сколько выбрано, кнопка `op-print` «Распечатать или сохранить PDF» (активна при выборе от 1), кнопка «Очистить выбор». Выбор живёт только в памяти страницы
- `#device=<код>` читается `readParams(['device','back'])`: код сверяется с `^\d{6}$` и с данными, строка отмечается, фрагмент стирается `history.replaceState`
- печатная часть уже отрисована сервером (`.dv-sheet`, только для `print`), JS лишь показывает выбранные строки:
  - `draft(legal)`, заголовок «Что просить: медицинские изделия для паллиативной помощи на дому»
  - на каждую позицию блок: вид по НКМИ, код, кто выдаёт (обе ветки при сноске 2), основание кратко (перечень, страница скана), и три пустые строки для ручки «Куда обратились», «Дата», «Что ответили»
  - строка `verified:false` в лист не попадает, вместо неё «Пункт не проверен и в лист не включён»
  - `op-sheet-footer`: «Данные от ..., сверьте до ...», адрес страницы текстом
  - до 6 позиций на A4, одна позиция = одна страница
- без JS: печать даёт всю таблицу перечня (это нормально, лист «что просить» требует JS)
- ссылки «Скачать CSV» и «Скачать JSON» на `data/v1/devices-398n.csv` и `.json`

### 2.4 `/channels/` Через кого получают

- H1 «Через кого получают изделия»
- две карточки:

  - «Соцфонд»: когда этот путь, основания `[[n:pp-240]]`, `[[n:2347-r]]`, п. 26 положения, сноска 2
- H2 «Если отправляют из одного места в другое»: `unverified` «Нормы для случая „инвалидность есть, а в ИПРА позиции нет“ мы пока не нашли» и кнопка «Попросить ответ на бумаге» → ok `oral-refusal`
- H2 «Документы ссылаются на отменённые»: две коллизии с цитатами
- процедуру не переписываем подробно: шаги только там, где есть цитата, остальное ссылкой на нормы

### 2.5 `/changes/` Что изменилось

- H1 «Что изменилось в перечне»
- строка с числами только по сверенным строкам: «В старом перечне [N] позиций, в новом [170], совпадают [M]». Если сверено не всё: «Старый перечень сверен не полностью: [k] строк ещё проверяются»
- H2 «Новое в перечне» списком со ссылками на карточки
- H2 «Нет в новом перечне»: у каждого кода якорь `#c-<код>` и слова из A11. Флаг `retired` (кода нет и в НКМИ) пишется «Этого вида больше нет в справочнике Росздравнадзора»
- H2 «Если отказывают из-за „пересмотра кодов“»: перечень действует с даты вступления в силу, коды в нём есть, кнопка «Попросить ответ на бумаге» → ok
- что поменяла поправка 1195н в старом перечне, одной строкой

### 2.6 `/nutrition/` и `/nutrition/<eo>/` Лечебное питание

- H1 «Лечебное питание»
- фраза: перечень специализированных продуктов лечебного питания для детей-инвалидов утверждён Правительством, у него три редакции
- лента редакций карточками: дата, «утверждён» или «изменения», с какого числа действует (если сверено), число страниц, первая фраза акта дословно, ссылка на публикацию. Ссылка «Подробнее» → `/nutrition/<eo>/`
- строка «Список продуктов мы пока не перенесли: в нём торговые наименования. Смотрите приложение в официальной публикации» и ссылка
- H2 «Продукта нет в перечне»: «Решение может принять врачебная комиссия» со статусом `unverified`, пока нет дословной цитаты нормы, ссылка `[[n:323-fz]]`
- H2 «После 18 лет»: «Взрослых обеспечивают по решениям регионов» со статусом `unverified`
- кнопка «Отказали в питании» → ok `case/#new=1&s=oral-refusal&nut=<eo базовой редакции>`

`pipeline.watch` пишет `_reports/watch.json` по PLATFORM §6.3. Шаги:

1. скачать `meta.csv`. Ошибка → `consecutive_failures + 1` в `last_check.json` (факт), при 3 подряд review `source_down`
2. версия та же → только `last_check.json` (факт)
3. новая версия → скачать zip, сверить имя структуры и sha256 XSD. Изменились → review `format_changed`, старый снимок остаётся
4. обновить `snapshots/nkmi.json` (факт)
5. код 398н пропал → review `code_removed` (issue на каждый код). Сайт после следующей сборки сам показывает карточке «Не проверено: кода нет в последней версии справочника»; это вычисляется из снимка, канон не меняется
6. имя вида в НКМИ не совпало с `398n.csv` → PR правки `nkmi_name` с меткой `review:medical` (это текст, который видят семьи)

Факты по умолчанию идут PR `watch/nkmi-facts` с меткой `facts`: после него ручной запуск checks и `gh pr merge --auto`, если в репо включено автослияние. Защищённый main бот не трогает. `scripts/watch-apply facts` (POSIX sh) коммитит и пушит снимок одним коммитом `data: снимок НКМИ <версия>` только при `WATCH_FACTS_PUSH=true`, когда для GitHub Actions настроен обход правил main. Правки имён идут PR через `peter-evans/create-pull-request`, issues через `gh issue create` с меткой `[watch:<sha256(kind+source) первые 12>]` в заголовке и поиском дубля перед созданием

Без человека в main попадает только `data/snapshots/*` и `raw/nkmi_subset.csv`. Никогда сам: `398n.csv`, `348n.csv`, `aliases.csv`, `quotes.yaml`, `channels.yaml`, `warnings.yaml`, `nutrition_3551r.csv`. Недоступный источник не валит `pages.yml`: сайт собирается на последнем снимке, а свежесть видна по двум датам

Не проверено и записано в STATUS: отвечают ли RZN и pravo раннерам GitHub. Расписание держит живым не коммит бота, а шаг `PUT .../actions/workflows/<файл>/enable` в конце watch и sync-data

### 6.1 Порядок старта

1. **Агент данных, первые шаги:** `site.yaml`, `pyproject.toml`, `scripts/sync-ui` и его запуск, 8 схем в `data/schema/`, 8 фикстур в `tests/fixtures/`, `pipeline/export.py` в режиме фикстур. После этого `uv run python -m opsite build` проходит, и агент сайта работает на фикстурах
2. дальше параллельно: данные (OCR, сверка, канон, watch) и сайт (шаблоны, поиск, лист, e2e)
3. когда канон готов, `export.py` перестаёт отдавать фикстуры, сайт пересобирается на реальных данных

### 6.2 Контракт

- сайт читает только `ctx.data[<dataset>]` (конверты из `export.py`) и `ctx.vendor['pal-norms']`, в браузере только `data/v1/*.json`
- поля элементов ровно по таблице 4.1 и схемам. Новое поле добавляет только агент данных, сначала в схему
- `channel_ids`, `warning_ids`, `nkmi_status`, `in_348n` вычисляет `export.py`, сайт логику канала не повторяет
- тексты в данных не содержат номеров актов, только токены `[[n:<norm_id>]]`
- поиск в браузере грузит `aliases.json` и `devices-398n.json` при первом фокусе в поле, плюс `devices-348n-diff.json` для кодов, которых нет в новом перечне
